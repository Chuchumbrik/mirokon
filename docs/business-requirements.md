# Бизнес-требования: Mirokon — сайт по установке пластиковых окон

> Версия 1.0 — составлено 2026-06-03 по итогам мульти-агентных продуктовых дебатов  
> Статус: живой документ, подлежит уточнению после получения реальных данных от заказчика

## 1. Видение и цель сайта

### Цель бизнеса
Конвертировать органический и рекламный трафик в лиды (заявки на замер/расчёт) для компании по установке пластиковых окон.

### JTBD (Jobs To Be Done)

**Посетитель сайта (потенциальный клиент):**
> "Помоги мне убедиться, что эта компания надёжная, дай мне примерно понять стоимость — чтобы я решился позвонить или оставить заявку."

Шаги: (1) увидел → (2) посмотрел примеры работ → (3) поиграл с конструктором → (4) оставил заявку / позвонил.

**Заказчик-оператор (владелец бизнеса):**
> "Дай мне простой способ добавлять фото новых работ, публиковать одобренные отзывы и писать редкие новости — не сложнее, чем Instagram."

### Кто пользователь
- **Первичный:** Частное лицо, планирующее замену или установку окон в квартире/доме/балконе. Возраст 28-55, ищет в Яндексе, сравнивает 2-3 компании. **Гео: Москва и Московская область** (подтверждено заказчиком 2026-06-03).
- **Вторичный:** Владелец или менеджер компании Mirokon — управляет контентом через админку.

## 3. Scope

### MVP (Must-have) — первый публичный релиз

#### Лендинг
- [ ] Исправленный index.html без entity-escaped кавычек (весь JS должен работать)
- [ ] Hero-секция с рабочей кнопкой "Рассчитать стоимость" (скролл к конструктору)
- [ ] Галерея работ — рендерится из БД (Supabase), не из захардкоженного HTML
- [ ] Секция отзывов — Swiper-слайдер работает, отзывы из БД (только одобренные)
- [ ] Секция новостей — 3 последних из БД
- [ ] Форма заявки (имя, телефон, комментарий) — реальная отправка в Telegram И Email
- [ ] Мобильная навигация (кнопка "Меню" сейчас не работает)
- [ ] Яндекс.Метрика с целью на submit формы

#### Конструктор окон (лид-магнит)
- [ ] Рабочий JS — корректная обработка всех 6 типов конструкций
- [ ] Явный дисклеймер: "Ориентировочная стоимость. Точный расчёт — бесплатно, за 10 минут."
- [ ] CTA сразу под ценой: "Уточнить у менеджера" → скролл к форме заявки или модалка с формой
- [ ] При нажатии "Добавить в заявку" — данные конструктора попадают в форму заявки как предзаполненный комментарий

#### Формы и лиды
- [ ] Форма заявки → отправка через Vercel Function (POST /api/lead) в Telegram И Email (nodemailer или Resend)
- [ ] Форма отзыва → /api/review (уже есть, нужно подключить к фронту)
- [ ] Валидация на фронте (телефон обязателен, имя обязательно)
- [ ] TG-токен вынести в переменные окружения Vercel (убрать из кода)

#### Бэкенд и БД
- [ ] Supabase: три таблицы — `works`, `reviews`, `news`
- [ ] Vercel Functions для публичного API: GET /api/works, GET /api/reviews (только approved), GET /api/news
- [ ] Supabase Auth для авторизации админки (один пользователь — владелец)

#### Админка
- [ ] Рабочая страница логина (сейчас landing.html сломана — entity-escaped HTML)
- [ ] После логина: три вкладки — Работы / Отзывы / Новости
- [ ] CRUD для каждой коллекции через Supabase API
- [ ] Модерация отзывов: поле `approved: boolean`, в админке список "на модерации" и "опубликованные"
- [ ] Загрузка фото для работ через Supabase Storage
- [ ] Выход из системы (logout)

#### Безопасность (блокер релиза)
- [ ] Удалить хардкод TG-токена из api/review.js → ENV Vercel
- [ ] Авторизация админки: JWT от Supabase Auth (не localStorage-флаг)
- [ ] Supabase Row Level Security: публичные таблицы — только чтение без auth, запись — только авторизованный пользователь
- [ ] HTTPS (обеспечивает Vercel автоматически)

- Интернет-магазин / корзина

## 5. Нефункциональные требования

### 5.1 Бэкенд и БД

- **Хостинг:** Vercel (статика + Vercel Functions для API)
- **БД:** Supabase (PostgreSQL) — бесплатный tier достаточен для MVP
- **Auth:** Supabase Auth (email/password, один пользователь)
- **Хранилище файлов:** Supabase Storage (для фото работ)
- **Email:** Resend (бесплатно до 100 писем/день) или SMTP через ENV
- **Telegram:** Telegram Bot API, токен только через Vercel ENV

### 5.2 Безопасность

- TG-токен, email-ключи — только в ENV Vercel, никогда в коде
- Supabase RLS: публичные таблицы → `SELECT` без auth; `INSERT/UPDATE/DELETE` → только auth
- Авторизация админки: Bearer JWT от Supabase Auth, проверяется на каждый защищённый API-запрос
- Отзывы: rate-limit на /api/review (не более 3 в час с одного IP) — защита от спама
- HTTPS: Vercel по умолчанию

### 5.3 Производительность

- Галерея: фото оптимизированы (WebP, < 200 КБ на изображение), CDN через Supabase Storage
- Tailwind CDN заменить на production build при достижении 50+ посетителей/день
- Первый contentful paint < 2 с на мобильном (LCP < 2.5 с)

### 5.4 Доступность и совместимость

- Мобильные устройства: адаптивная вёрстка (уже заложена в Tailwind)
- Браузеры: Chrome, Safari, Firefox — последние 2 версии
- Минимальная ширина экрана: 320px

## 7. Журнал решений (Decision Record)

### DR-001: Конструктор окон — оставить в MVP
**Дата:** 2026-06-03  
**Вопрос:** Включать ли конструктор окон в MVP или перенести в v2?  
**Решение:** Оставить в MVP с условиями.  
**Обоснование:**  
- product-advocate: единственный интерактивный элемент, удерживающий посетителя; отраслевой стандарт как лид-магнит; психологически "вовлекает" в покупку.  
- devil-advocate: предупредил — без корректного JS и реальных цен конструктор наносит вред репутации.  
- business-advocate: +15-40% конверсии по отраслевым данным, при наличии явного дисклеймера.  
**Условия включения в MVP:** (1) исправлен JS без entity-escaped кавычек, (2) все 6 типов конструкций имеют логику расчёта, (3) дисклеймер "ориентировочная стоимость" неотъемлем, (4) CTA "уточнить у менеджера" прямо под ценой.  
**Сильнейший контраргумент (devil):** "Пользователь видит цифру 20 026 ₽, звонит менеджеру, получает другую — и теряет доверие. Если заказчик не даст хотя бы порядок цен, конструктор лучше убрать."

---

### DR-002: Архитектура бэкенда — Supabase + Vercel Functions, без headless CMS
**Дата:** 2026-06-03  
**Вопрос:** Строить ли кастомную CMS, использовать headless CMS (Strapi/Directus) или Supabase?  
**Решение:** Supabase (PostgreSQL + Auth + Storage) + Vercel Functions + кастомный минималистичный admin.html.  
**Обоснование:**  
- devil-advocate: Strapi требует отдельного сервера, несовместим с serverless Vercel. Supabase устраняет этот overhead.  
- product-advocate: согласился с Supabase-вариантом после уточнения.  
- user-empathy: кастомный admin.html "три вкладки" проще для владельца бизнеса, чем сложный CMS-интерфейс.  
- business-advocate: Supabase free tier покрывает MVP, TCO минимален, нет отдельного сервера.  
**Отклонённые варианты:**  
- Strapi: несовместим с Vercel serverless архитектурой.  
- Telegram-управление контентом: неприемлемо для структурированных данных и фото, подходит только для лидов.  
- Кастомная Node.js CMS с нуля: 3-4 недели работы ради повторения того, что Supabase даёт из коробки.

---

### DR-003: Security — блокер релиза, не v2
**Дата:** 2026-06-03  
**Вопрос:** Когда устранять security-проблемы — до или после релиза?  
**Решение:** До релиза. Security — блокер.  
**Обоснование:**  
- devil-advocate: "TG-токен в открытом коде на GitHub — это не 'риск', это уже компрометация."  
- business-advocate: "Утечка TG-токена → спам в рабочий чат → пропуск реальных лидов. Прямой бизнес-ущерб."  
**Конкретные действия:** (1) TG-токен + email-ключи → ENV Vercel, удалить из кода; (2) авторизация админки → JWT от Supabase Auth; (3) Supabase RLS; (4) текущий TG-токен в api/review.js считать скомпрометированным — создать нового бота.

### DR-004: Фейковый контент — убрать до публичного деплоя
**Дата:** 2026-06-03  
**Вопрос:** Деплоить ли сайт с фейковыми отзывами и цветными квадратами вместо фото?  
**Решение:** Нет. Фейковый контент убрать или заменить нейтральными заглушками.  
**Обоснование:**  
- user-empathy: "Фейковые отзывы и цветные квадраты вместо фото РАЗРУШАЮТ доверие быстрее, чем любой баг. Лучше 0 отзывов, чем очевидно фейковые."  
**Допустимо на старте:** пустые секции с сообщением "Скоро здесь появятся наши работы" или нейтральные placeholder-тексты без имён реальных людей.

**Дата:** 2026-06-03

### DR-006: Тестовая фаза — уточнение к DR-003 (security как блокер)
**Дата:** 2026-06-03  
**Вопрос:** DR-003 требует отзыва скомпрометированного TG-токена до релиза. Заказчик сознательно откладывает это действие. Противоречие?  
**Решение:** Противоречия нет. DR-003 остаётся в силе. Уточнение: проект сейчас находится в **тестовой фазе** на тестовом боте и заглушках — публичного релиза не было. Отзыв токена и вынос секретов в ENV обязателен **перед публичным релизом**, а не прямо сейчас.  
**Обоснование заказчика:** старый токен сожгут после завершения тестов, не раньше — чтобы не прерывать тестовый процесс.  
**Позиция devil-advocate (сохраняется в силе):** "Токен в открытом коде на GitHub — уже компрометация. Тестовый бот используется осознанно, на ограниченный срок, на собственный страх и риск. Это приемлемо только потому, что это тестовый бот, а не рабочий чат с реальными лидами."  
**Статус DR-003:** не отменён, не изменён. Все четыре действия из DR-003 остаются блокерами публичного релиза — теперь продублированы в чек-листе 6.1.  
**Ключевая цитата:** "Тестовая фаза идёт на тестовом боте и заглушках — это сознательное решение. Перед тем как открыть сайт публике, все security-пункты должны быть закрыты без исключений."

### 8.1 Дизайн-система (основа редизайна)

Дизайн-система фиксируется **перед** началом поблочной проработки и служит единственным источником истины для визуальных решений.

#### Токены (обязательно зафиксировать)

| Категория | Что определить |

| Типографика | Шкала размеров (xs/sm/base/lg/xl/2xl/3xl), межстрочные интервалы, font-weight |

| Состояния | hover / focus / active / disabled — единообразные по всем компонентам |

### DR-007: Полный редизайн + дизайн-система и поблочная глубокая проработка по DoD
**Дата:** 2026-06-03
**Вопрос:** Нужен ли полный редизайн сайта и единый стандарт качества для каждого блока?
**Решение:** Да. Полный редизайн на основе дизайн-системы. Каждый блок проходит поблочный DoD из трёх обязательных измерений (Визуал+UX, Код+тесты, Производительность+конверсия).
**Инициатор:** заказчик (2026-06-03).
**Обоснование:**
- Текущий визуал использует дефолтный Tailwind blue-600 — выглядит генерично, не формирует доверие.
- Качество проработки разнится по блокам: часть сделана хорошо, часть содержит баги, заглушки и незакрытые состояния.
- Единая дизайн-система + поблочный DoD устраняют оба недостатка: дают консистентный визуал и управляемый уровень качества на каждом этапе.
- Инкрементальный подход (один блок → гейт → следующий) снижает риск регрессий и даёт измеримый прогресс.

**Осознанные компромиссы:**
- a11y (доступность) и SEO выведены в «рекомендуемые» — не обязательные — измерения DoD. Причина: SEO уже запланирован в v2; a11y требует отдельных усилий и не является блокером первичного релиза. Оба пункта остаются в бэклоге и могут быть повышены до обязательных по решению заказчика.

**Позиции агентов:**
- product-advocate: дизайн-система — правильное стратегическое решение; единый DoD снижает технический долг.
- devil-advocate: поблочный подход замедляет общую скорость; риск — блоки в разных состояниях готовности долгое время. Принято осознанно.
- user-empathy: пользователь замечает несогласованность раньше, чем думает команда; консистентность важна для доверия.
- business-advocate: 152-ФЗ (согласие + политика) и XSS в админке — блокеры релиза независимо от порядка проработки.

**Ключевая цитата:** «Сайт должен быть проработан полностью — от дизайна до оптимизации каждого блока. Генеричный шаблонный вид и разный уровень готовности блоков — неприемлемо для финального продукта.»

### DR-008: Портфолио-кейсы — галерея превращается в объекты работ с детальным видом
**Дата:** 2026-06-04
**Вопрос:** Как превратить галерею (карточка = обложка + title + category + description) в полноценные кейсы-объекты с детальным видом, перечнем работ, ценовым ориентиром и переходом в конструктор — и что входит в первый срез (MVP)?

**Решение:** `proceed-with-modifications`. Реализовать MVP-кейсы с фазировкой в два этапа.

**MVP (первый срез):**
- Схема: добавить в `works` поля `category`, `scope text[]`, `system`, `duration_days`, `area`, `warranty`, `price_from int`
- Фильтры-чипы по категориям (Спальня / Кухня / Балкон / Лоджия / Офис) над сеткой
- Детальный вид через оверлей с FLIP-анимацией (переиспользовать паттерн модалок); fallback — fade
- Hash-фрагмент `#work/{id}` для shareable URL; полноценные SEO-страницы — V2
- Отображение: большое фото + миниатюры (work_photos) + перечень работ + система/срок/район/гарантия + «от X ₽» + disclaimer
- CTA «Рассчитать для моей квартиры» — открывает конструктор с предзаполненным типом окна; полный шаблон (`template jsonb`) — V2
- Информер: «Стоимость аналогичного объекта. Точный расчёт — после бесплатного замера за 24 часа.»
- Метрика: события `portfolio_open`, `portfolio_to_calculator` в Яндекс.Метрике
- Контентный блокер: фичу не включать публично до наличия ≥ 4 кейсов с реальными фото

**V2 (после накопления 10+ кейсов с фото «до»):**
- Before/after слайдер (только с реальными фото, не постановочными)
- Полный `template jsonb` → загрузка нескольких позиций в корзину конструктора
- Отдельные SEO-страницы `/works/{id}` с meta/title/description/Schema.org

**Зафиксированные решения заказчика (данность, не оспаривалась):**
1. Цена — только «от X ₽», без итоговой суммы проекта (логика DR-001)
2. Детальный вид — оверлей с FLIP-анимацией, не inline-раскрытие сетки

**Обоснование (позиции агентов):**

- **product-advocate (поддержка):** Конкретность кейса («трёхстворчатое VEKA, спальня, Жуковский, 3 дня») резко отличает от конкурентов с «просто фотогалереей». Фильтры по категориям — язык пользователя (он думает комнатами, не типами окон). `template jsonb` — стратегический актив для V2. Hash-фрагмент — правильный компромисс SEO/UX на старте.
- **devil-advocate (поддержка с условиями):** Фича правильная, но три блокера: (1) контентная яма — 0 фото сейчас делают детальный вид бессмысленным; (2) информер «ориентировочная цена» без обещания = «разводят»; (3) FLIP на Safari iOS даёт сдвиг геометрии — обязателен fallback. Все три закрыты условиями MVP.
- **user-empathy (поддержка):** Персона (Алексей, 38, Люберцы) узнаёт себя в кейсе по категории и району. Перечень работ снимает главное незнание: «что вообще входит?». Срок «2 дня» важнее, чем кажется — снимает страх «будут неделю». CTA «Рассчитать для моей квартиры» снижает барьер персонализацией.
- **business-advocate (поддержка):** Кейс закрывает три возражения одновременно: «умеют?», «что входит?», «приедут?». Микроконверсия «смотреть → считать» через «Рассчитать для моей квартиры» измерима. `price_from` должна быть реалистичной — нижняя граница реальной сметы, не акционная.

**Осознанные компромиссы:**
- Before/after перенесён в V2, хотя психологически сильный триггер. Причина: без реальных фото «до» это будет маркетинговая постановка, разрушающая доверие (DR-004).
- Hash-фрагмент вместо полноценных SEO-страниц. Причина: 7 кейсов сейчас не дают SEO-ценности; индексировать пустые/малонаполненные страницы контрпродуктивно.
- «Рассчитать похожее» в MVP открывает конструктор с типом окна, а не полным шаблоном. Причина: нередактируемый шаблон в корзине раздражает; полный `template jsonb` — в V2 вместе с UX для его редактирования.

**Сильнейший контраргумент (devil-advocate):**
> «Сейчас 7 объектов и 0 фото. Если релизить фичу в этом состоянии — детальный вид открывается на пустую галерею. Пользователь, который кликнул на кейс в надежде увидеть реальную работу, видит шаблон. Это хуже, чем отсутствие детального вида вообще. Фичу нельзя публично включать до наполнения контентом.»

**Метрики успеха:**

| Метрика | Цель | Как измерять |
|---|---|---|
| CTR карточки кейса | > 20% посетителей галереи | Яндекс.Метрика, событие `portfolio_open` |
| Конверсия кейс → конструктор | > 10% открытий | `portfolio_to_calculator` / `portfolio_open` |
| Среднее время в кейсе | > 45 сек | Яндекс.Метрика |
| Рост лидов через 2 нед. после релиза | +30% к базовому | Сравнение недельных лидов до/после |
| Лиды с атрибуцией к портфолио | Отдельная метрика | utm_source=portfolio на кнопке CTA |
